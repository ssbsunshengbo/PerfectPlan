# Issue 分级与发布阻断规则

所有新 Issue 先标记 `status: needs-triage`，由维护者在确认问题和影响范围后补充类型、优先级与状态标签。不要在公开 Issue 中上传真实任务、数据库、证书、令牌或含有私人内容的截图。

## 标签体系

| 类别   | 标签                   | 含义                                          |
| ------ | ---------------------- | --------------------------------------------- |
| 类型   | `type: bug`            | 已有功能与预期不符                            |
| 类型   | `type: feature`        | 需要讨论的新能力或改进                        |
| 类型   | `type: feedback`       | 使用感受、困惑和非确定性建议                  |
| 状态   | `status: needs-triage` | 尚未确认、分级或排期                          |
| 状态   | `status: confirmed`    | 已复现或确认有效，等待排期/修复               |
| 优先级 | `priority: p0`         | 立即处理的严重问题                            |
| 优先级 | `priority: p1`         | 下一次发布前应修复的重要问题                  |
| 优先级 | `priority: p2`         | 有影响但可排期处理的问题                      |
| 发布   | `release-blocker`      | 阻止当前 Release 发布，直到关闭或获得书面豁免 |

`accessibility`、`documentation`、`good first issue` 等现有辅助标签可与上述标签并用。

## 优先级定义

### P0：立即阻断

- 任务数据丢失、损坏或被错误覆盖；
- 应用无法启动、持续崩溃，或主要平台完全不可用；
- 严重隐私或安全问题，例如未经同意上传用户数据；
- 任务完成、删除、日程安排等核心写入操作产生错误结果且无恢复路径。

P0 必须标记 `release-blocker`。在修复、回归验证和关闭前，不允许发布任何正式版或 Beta；唯一例外是维护者明确记录的紧急撤回/安全缓解发布。

### P1：下个版本前修复

- 核心流程明显受阻，但存在安全可行的绕过方式；
- 提醒、日历拖拽、搜索、无障碍键盘流程在常见场景下失效；
- 安装或升级会让一部分目标用户无法使用，但不会损坏数据。

计划发布前，所有已确认 P1 都应修复并验证；若确有延期，需要在 Release 说明中写明范围、绕过方式和目标修复版本，并由维护者明确批准。

### P2：排期改进

- 视觉瑕疵、文案问题、低频边界场景或非核心体验改进；
- 不影响数据完整性、安全、主要任务流程或基本无障碍使用。

P2 不阻断发布，仍应被归类、去重并在产品反馈中定期复核。

## 处理流程

1. 在 3 个工作日内确认、补充信息或标记重复/无效。
2. 对已确认问题补上一个 `priority:` 标签；需要阻断发布时同时加 `release-blocker`。
3. 修复 PR 必须关联 Issue，包含可复现的验证结果；涉及数据、隐私或权限时还需更新相应文档或 ADR。
4. 发布前检查所有未关闭的 `release-blocker`、P0 和 P1；不满足规则时将 Release 保持为草稿。
