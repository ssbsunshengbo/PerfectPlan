# PerfectPlan 实施计划

> 状态：阶段 1、2 已完成；阶段 3 已完成每日规划闭环；阶段 4 已完成时间安排与本地提醒；阶段 5 的数据导入导出与备份按产品决定暂缓，其余质量保障已完成；阶段 6 正在推进发布准备。
> 更新方式：每完成一个任务包，更新本文件中的状态、决策和风险；不以口头约定代替文档。

## 1. 目标与边界

PerfectPlan 是面向个人用户的、离线优先的桌面计划软件。用户下载后无需注册即可管理任务、规划每天并安排时间。个人数据默认只保存在设备本地。

### 1.1 MVP 成功标准

MVP 必须让用户独立完成以下闭环：

1. 用极低成本将任务记录到收集箱；
2. 从任务中挑选今天的重点；
3. 为任务安排日期和时间，并在日历中调整；
4. 完成、延期或取消任务而不丢失上下文；
5. 离线使用、备份并取回自己的数据。

### 1.2 MVP 不包含

- 账号体系、云端同步、协作、共享任务；
- Google、Outlook 或 Apple 日历集成；
- iOS、Android、网页端；
- 习惯、番茄钟、AI 助手、复杂统计、附件和模板市场；
- 团队项目、权限和付费功能。

这些内容只在 MVP 验证后，按真实用户反馈排入后续版本。

## 2. 已定技术决策

| 领域     | 决策                                                | 原因                                     |
| -------- | --------------------------------------------------- | ---------------------------------------- |
| 桌面壳   | Tauri 2 + Rust（包标识：`com.perfectplan.desktop`） | 安装包轻、原生能力足够、适合本地优先应用 |
| 前端     | React + TypeScript + Vite                           | 组件生态成熟，迭代速度快                 |
| 本地数据 | SQLite + 数据库迁移                                 | 离线可靠、可检索、便于备份与未来同步演进 |
| 状态     | React Query/轻量 Store + 服务层                     | UI 状态与持久化业务逻辑分离              |
| 样式     | Tailwind CSS + 自建无障碍组件规范                   | 快速建立一致的桌面界面                   |
| 测试     | Vitest + Playwright + Rust 单元测试                 | 保障规则、关键流程与打包质量             |
| 发布     | GitHub Actions + GitHub Releases                    | 无自建分发服务器                         |
| 官网     | 静态站点 + GitHub Pages                             | 展示、下载、隐私与开源入口               |

## 3. 产品与数据原则

- **本地优先**：应用在断网下完整可用；联网只用于用户明确发起的下载、更新或反馈。
- **任务时间语义清晰**：计划时间、截止时间和提醒时间分开保存与呈现。
- **先快速、后完善**：创建任务时只需要标题；其他属性逐步补充。
- **可恢复而非惩罚**：完成可撤销，删除进回收站，未完成任务可一键改期。
- **用户拥有数据**：可导出完整 JSON；应用不锁定用户数据。
- **免费核心能力**：任务、项目、提醒、日历、筛选和本地备份不设数量限制。

- [x] `P0-02` 确定信息架构：今日、收集箱、即将到来、日历、项目、设置。

任务包：

- [x] `P1-01` 初始化 Git 仓库、开源许可证、贡献指南、问题模板和行为准则。
- [x] `P1-02` 初始化 Tauri 2 + React + TypeScript 工程；配置格式化、Lint、类型检查和提交前检查。
- [x] `P1-03` 建立应用壳：侧栏、主内容区、命令面板入口、深浅色主题和响应式窗口布局。
- [x] `P1-04` 设计 SQLite schema、迁移框架、仓储层和事务边界。

验收条件：离线创建测试任务，重启应用后数据无损；数据库迁移可从空库稳定执行；CI 在干净环境通过。

### 阶段 2：任务管理闭环

目标：让用户可以用 PerfectPlan 替代最基本的待办清单。

任务包：

- [x] `P2-01` 收集箱与快速添加：标题必填、回车创建、连续添加、撤销。
- [x] `P2-02` 任务详情：备注、优先级、项目、标签、子任务、日期字段。
- [x] `P2-03` 项目/清单：创建、重命名、排序、归档、颜色与任务迁移。
- [x] `P2-04` 标签：创建、选择、筛选、删除时的任务保留策略。
- [x] `P2-05` 完成、恢复、软删除与回收站；所有危险操作可撤销或确认。
- [x] `P2-06` 全文搜索和基础筛选。
- [x] `P2-07` 全局快捷键和键盘导航；不依赖鼠标即可完成主要操作。

验收条件：用户可管理 1,000 条任务；常用操作有即时反馈；任务修改、完成、删除都不会造成数据丢失。

### 阶段 3：每日规划

目标：从“存放任务”变为“帮助决定今天做什么”。

任务包：

- [x] `P3-01` 今日视图：重点、已计划、逾期和已完成区域。
- [x] `P3-02` 即将到来：默认未来 7 天，支持按日期浏览。
- [x] `P3-03` 日期与时间选择器；创建任务不强制填写时间。
- [x] `P3-04` 常用重复规则：每天、工作日、每周、每月，以及完成后生成下一次实例的规则。
- [x] `P3-05` 一键改期：今晚、明天、下周、未指定日期。
- [x] `P3-06` 每日收尾：未完成任务回到原项目，同时出现在下一日的建议区域；不自动伪造“已完成”。

验收条件：用户可在两分钟内完成当天计划；跨日后未完成任务仍可理解、可找回、可重新安排。

### 阶段 4：时间安排与提醒

目标：提供免费且可信的时间块规划体验。

任务包：

- [x] `P4-01` 日历日视图和周视图，支持按时间排序的未排期任务区，以及月视图日期概要与导航。
- [x] `P4-02` 拖入、拖动、拉伸任务时间块；提供 8 秒撤销与键盘等价的“安排到…”操作。冲突和超载提示移至 P4-03。
- [x] `P4-03` 预计时长、全天任务与有具体时间的任务显示规则；冲突、超载与异常时间块均以非阻断提示呈现。
- [x] `P4-04` 本地提醒管理：单次提醒、重复任务按相同相对时间延续提醒、权限拒绝时的引导。提醒会在应用运行期间触发；完全退出后的行为留待 P4-06 明确。
- [x] `P4-05` 提醒操作：完成、30 分钟后提醒、明天同一时间提醒、打开任务。桌面端以应用内提醒中心承载操作；原生通知按钮仅由当前 Tauri 插件在移动端支持。
- [x] `P4-06` 已完成后台运行/自动启动可行性验证：MVP 不引入托盘常驻或自动启动；应用运行期间提醒，完全退出后不触发提醒。详见 `docs/decisions/ADR-0002-reminder-background-policy.md`。

验收条件：用户可安排一周任务、用拖拽改期，并能理解当天是否超载；提醒不会静默失败或无限骚扰。

## 6. 完成定义（Definition of Done）

每个任务包只有同时满足以下条件才标记完成：

1. 功能在目标平台可实际操作，不只存在于代码或设计稿；
2. 核心业务规则有自动化测试，或记录了无法自动化的手测步骤；
3. 空状态、加载状态、错误状态和撤销/恢复路径已考虑；
4. 无意外的控制台报错、类型错误或 lint 错误；
5. 不扩大 MVP 范围；新增依赖或权限已写入决策记录；
6. 更新本计划的状态与已知风险。

## 7. 协作方式

### 每次工作会话

1. 从本文件选择一个最小任务包；避免同时推进多个相互依赖的功能。
2. 先确认目标、影响文件、测试方式和不做什么。
3. 实现后运行相应检查，记录结果与剩余风险。
4. 我会给出可审阅的变更摘要、文件链接和下一项建议；你决定是否继续、调整范围或发布。

### 决策记录

- 扩大系统权限；
- 调整 MVP 边界；
- 选择影响长期维护成本的框架或发布方式。

## 8. 风险与应对

| 风险                           | 影响         | 应对                                                        |
| ------------------------------ | ------------ | ----------------------------------------------------------- |
| 日历拖拽范围膨胀               | 延迟 MVP     | 仅日/周视图；不做外部日历同步与复杂资源调度                 |
| 本地提醒在应用退出后失效       | 损害信任     | 在阶段 4 做平台验证；无法可靠支持时延后承诺，并清晰告知用户 |
| macOS 签名/公证与 Windows 签名 | 用户安装受阻 | 发布阶段前确认开发者账户和证书；先以 Beta 方式测试          |
| 数据库 schema 频繁变动         | 数据损坏     | 从阶段 1 起使用迁移、自动备份和升级测试                     |
| 需求不断扩张                   | 首发拖延     | 一切新增功能先进入 `docs/BACKLOG.md`，不插入进行中阶段      |
| 没有遥测，难以量化使用         | 优化方向不清 | 使用自愿反馈、GitHub Issues、用户访谈和匿名可选诊断包       |
